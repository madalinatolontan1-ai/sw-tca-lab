Software Test Coverage Analysis (SW TCA)

What is SW TCA?

In HW TCA the board is designed correctly, but every manufactured unit can come out with its own defect (a missing part, an open solder joint), so every board goes through the production tests. Software is not manufactured unit by unit: every module shipped contains exactly the same program. If a programmer wrote >= instead of >, the mistake is in every module, from day one. ISO 26262 calls these mistakes systematic faults; for software, all faults are systematic.

A software fault cannot be caught in production, because all units are identical. The code is verified once, during development, and again at every change (regression testing). Software Test Coverage Analysis (SW TCA) answers the question: how completely have the tests exercised the code and the requirements? Is there a line that no test has executed? If there is, any mistake in it is certain to reach the customer.

ISO 26262 does not set a percentage: it asks for a defined and justified target value (ISO 26262-6, 9.4.4, NOTE 1: a missing or too low target without a justification is insufficient). In industrial practice the usual target is 100%, required by vehicle manufacturers in their customer-specific requirements and by the aviation standard DO-178C. In the lab we also work with 100%. What cannot be covered by tests is justified in writing: why it cannot be reached and why that is acceptable. It is the counterpart of the residual risk in HW TCA.

Coverage is measured with metrics. The ones used in the lab are:

MetricWhat it checksGood at findingLimits
Statement coverageEvery statement has been executed at least once.code never executed (a return, a branch with statements)does not see the false branch of an if without else
Branch coverageEvery decision (if, switch) has been both true and false.untested outcomes of a decisiondoes not see the conditions inside a decision with && or ||

None of the metrics says whether the result is correct. Only the expected result of the test, taken from the requirement, does that.

What the standards require

The functional safety standard for road vehicles, ISO 26262 (2018 edition), part 6, recommends the metrics according to the ASIL (Automotive Safety Integrity Level, from A to D, D being the strictest). ++ means highly recommended (in practice mandatory; if it is not applied, a justification is written), + means recommended.

MetricASIL AASIL BASIL CASIL D
Statement coverage (unit, table 9)++++++
Branch coverage (unit, table 9)+++++++
MC/DC (unit, table 9)+++++
Function coverage (integration, table 12)++++++
Call coverage (integration, table 12)++++++

Entries 1a, 1b and 1c of table 9 are alternatives: a combination suited to the ASIL is chosen, with a justification. At ASIL B, statement and branch coverage are ++, while MC/DC is only +. Structural coverage at integration (clause 10.4.5, table 12) applies to ASIL A and B only as a recommendation: the standard writes „ASIL (A), (B), C and D”, and the brackets mean a recommendation. In the lab we practise it as good practice. If the coverage reached is considered insufficient, the standard requires either additional tests or a justification based on other methods (clause 9.4.4). Tests are written from the requirements, and Automotive SPICE, the model vehicle manufacturers use to assess their suppliers, requires every test to be linked to the requirement it verifies.

Case study: the firmware of the front radar's CAN node

We work on the same generic automotive front radar as in HW TCA (lab assumption: ASIL B), which sends the list of detected objects over CAN at 500 kbit/s, every measurement cycle (about 72 ms). The firmware of the CAN node has four C functions. The code was written for the lab, following real rules: the CAN limits come from ISO 11898-1, and the sensor ranges are typical values for a long-range automotive radar. The app shows, for every value, where it comes from. One exception to keep in mind: in classic CAN a DLC of 9…15 is valid at protocol level and still means 8 data bytes. Rejecting a DLC greater than 8 (SWR-F1-01) is therefore a requirement of our application, chosen for robustness, not a rule of the CAN protocol.

Write the tests (the inputs, the expected result from the requirement and the requirement verified) and press „Run tests”. The code is coloured like a coverage report: the number next to a line shows how many times it ran, ##### means a line not executed, and the T and F labels show whether the decision was true or false. Every tab also has three aids: „Context: what the function does”, „How to do it” (the steps) and „Where the values come from” (where every constant in the code comes from). If you hold the mouse over a column name, a percentage or a #define line, the app explains what it means. The app also checks every test against the requirements: if a test does not exercise the requirement it declares, or if the expected result contradicts the requirement, a warning appears under the test, and the warnings go into the report. A failing test is an incident (the term from ISO/IEC/IEEE 29119-1; ISO 26262-2, 5.4.3.2 requires a process for resolving anomalies). The app shows the probable cause: „the test”, if the expected result contradicts the requirement, or „the code”, if the test follows the requirement and is therefore a fault to analyse in the incident report.

The app is a teaching simulator, not a qualified tool. In a real project, coverage comes from a commercial coverage tool assessed according to ISO 26262-8, clause 11. First the tool impact (TI) is determined: a coverage tool does not insert mistakes into the code, but it can report coverage wrongly and so hide a missing test, so it is TI2. Then the likelihood that a tool error is detected is determined (TD1–TD3). The two give the tool confidence level (TCL1–TCL3); for TCL2 and TCL3 the tool is qualified, usually with the qualification kit offered by the vendor. Tests run on instrumented code, and ISO 26262-6, 9.4.4, NOTE 4 requires showing that the instrumentation does not change the results.

Statement coverage and branch coverage

A test follows a single path through the function. In F3, every return is the end of a different path, so 100% statement coverage needs at least three tests:

1if (tec > CAN_BUSOFF_LIMIT) {                    /* 255 */
2    return CAN_STATE_BUS_OFF;
3}
4if ((tec > CAN_PASSIVE_LIMIT) || (rec > CAN_PASSIVE_LIMIT)) {  /* 127 */
5    return CAN_STATE_ERROR_PASSIVE;
6}
7return CAN_STATE_ERROR_ACTIVE;

TesttecrecResultCovers
T13000BUS_OFFline 2
T22000ERROR_PASSIVEline 5
T300ERROR_ACTIVEline 7

Branch coverage requires every decision to be true once and false once. In F1, if (extended) { max_id = …; } has no else. If every test has extended = true, every statement runs (100% statement), but the standard frame has not been tested at all: the false branch has no statement of its own, so statement coverage does not see it. That is why branch coverage includes statement coverage, but not the other way round.

Two details of F3 matter for coverage. The order: bus-off is checked before error passive; otherwise tec = 300 would come out ERROR_PASSIVE. The type: tec and rec are uint16_t. If they were uint8_t (0…255), the condition tec > 255 could never be true, and line 2 would be dead code: no test suite could cover it. The coverage analysis would reveal a problem in the requirements or in the design, not a missing test (ISO 26262-6, 9.4.4, EXAMPLE 1). The thresholds come from the CAN specification: error passive when a counter reaches 128, bus-off when TEC reaches 256.

MC/DC

A decision can have several conditions joined by && or ||. The decision at line 4 of F3 has two: A = (tec > 127) and B = (rec > 127). Branch coverage only looks at the result of the decision: with tests T2 and T3, B was never true, and a mistake in B (for example rec > 1270) would go unnoticed. MC/DC requires every condition to show that, on its own, it changes the result: for every condition there is a pair of tests in which only that condition changes, and the result changes too.

TesttecrecABA || B
T300falsefalsefalse
T22000truefalsetrue
T40200falsetruetrue

The pair T3–T2 shows A, the pair T3–T4 shows B. For N conditions, the theoretical minimum is N + 1 tests (unique-cause MC/DC, FAA report DOT/FAA/AR-01/18), instead of all 2^N combinations. It is not an ISO 26262 requirement: the standard only lists MC/DC in table 9 and does not define a particular form. For AND (&&) start from „all true” and make one condition false at a time; for OR (||) start from „all false” and make one true at a time. In C, && and || stop when the result is certain (short-circuit evaluation): in the app's truth table, a condition that was not evaluated is shown as „–”, and a pair is also valid if it differs only in conditions that were not evaluated. The form used by the app, unique-cause with short-circuit evaluation, is called unique-cause + masking MC/DC in the FAA terminology.

How tests are written, and why 100% does not mean free of mistakes

Tests are written from the requirements, not from the code (ISO 26262-6, table 8). At ASIL B, requirements analysis, equivalence classes and boundary values are all ++. The techniques are:

TechniqueWhat you doExample on F3 (bus-off when TEC > 255)
Requirements analysisAt least one test per requirement; the expected result comes from the requirement.tec = 300 → BUS_OFF
Equivalence classesSplit the range into groups that are handled the same way and take one value from each.TEC 0…127, 128…255, 256…65535
Boundary valuesTest the value exactly at the boundary and the one just past it: ISO 26262-6, table 8, note b asks for values that approach and cross the boundary, so a boundary is fully tested only with both. This is where > instead of >= mistakes live.TEC 127 / 128 and 255 / 256; REC 127 / 128
Error guessingValues chosen from experience.0, 65535, a difference of exactly zero

Coverage shows that a line ran, not that it gave the correct result. You can go through every branch with „middle” values and never touch the wrong boundary. The right order is: tests from the requirements, then the coverage, then the gaps.

Boundary values are mandatory in this lab. It is the same technique as in general software testing, called boundary value analysis (BVA): you find it in the ISTQB syllabus and in ISO/IEC/IEEE 29119-4; it is not specific to the automotive industry. The recipe has three steps: (1) find the number in the requirement; (2) ask yourself which is the last value with one answer and the first value with the other answer; (3) those two are the tests. Example: „ERROR_PASSIVE when REC > 127” gives REC = 127 (ERROR_ACTIVE) and REC = 128 (ERROR_PASSIVE). Values far from the boundary, such as 0 or 200, go through all the code, but do not see whether the programmer wrote >= instead of >: both versions of the code give the same result. In the app, the „Boundary values (BVA)” metric shows how many boundaries have both tests and must reach 100% in F1, F2 and F3, and the list under it shows which boundary and which test is missing.

A failing test is an incident. Its analysis shows that the expected result follows the requirement, so the cause is in the code: line 14 says id >= max_id instead of id > max_id. Integration and code that cannot be reached

At integration, the function can_rx_handler calls the other three. Here we track function coverage (every function called) and call coverage (every call site executed). What remains uncovered is analysed: a test is missing, a requirement is missing, or the code cannot be reached. Code that cannot be reached is not deleted if it has a role (for example defensive code, required by the MISRA C coding rules); it is justified: why it cannot be reached, why that is acceptable and how it could still be verified. For the default branch of a switch, ISO 26262-6, 9.4.4 accepts two ways. The first is the justification: it is defensive code, required by MISRA C:2012 rule 16.4 (every switch has a default), and ISO 26262-6, table 1, note d even gives default as an example of a defensive technique. The second is a test by fault injection (table 7, 1l, recommended at ASIL B): a stub of the function can_error_state() or the debugger forces state to an invalid value, for example 0xFF, and the test checks that the function returns RX_FAULT.

Integration: justification of the uncovered code

Lines 67–68 (default) cannot be reached by tests: can_error_state() returns only ERROR_ACTIVE, ERROR_PASSIVE and BUS_OFF, all handled explicitly.
